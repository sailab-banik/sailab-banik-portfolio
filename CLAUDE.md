## Project state

Single-page portfolio for Sailab Banik, built and live. `src/app/page.tsx` composes `Header`, `Hero`, `Experience`, `Projects`, `Writing` (which holds Toolbox and Credentials too), and `Footer` from `src/components/`.

The design reference is the exported mockup in `assets/design/` (`Main.dc.html`; gitignored). Its inline styles are the source of truth for values; it is not code to copy.

Exactly one client component exists, because it holds state: `section-tabs.tsx` (which header tab is current, from scroll position). Everything else is a server component; keep it that way unless a feature genuinely needs state.

There is deliberately no resume section. The mockup had one (a preview/source viewer); it was removed because it repeated Experience, Projects, and Toolbox. The resume is the PDF, opened in a new tab from the header, hero, and footer.

`PLAN.md` holds the design direction, content model, and the open gaps — read it before adding UI, and update it in the same commit when a design decision changes. It has contradicted the code more than once.

## Stack notes that differ from older Next.js/Tailwind

- **Next.js 16 App Router.** All routes live under `src/app/`. Read the version's own docs in `node_modules/next/dist/docs/` (see AGENTS.md) before using an API from memory.
- **Route component props are globally generated types**, not hand-written. Use `PageProps<"/some/route">` and `LayoutProps<"/some/route">` — declared in `.next/types/routes.d.ts`, regenerated by `next dev`/`next build`. `params` and `searchParams` on them are Promises and must be awaited. After adding a route, run dev or build so the types pick it up; TS errors about an unknown route string usually mean stale generated types.
- **Dev artifacts go to `.next/dev/`**, production ones to `.next/`. Both are gitignored.
- **Tailwind CSS v4** — there is no `tailwind.config.*`. Configuration is CSS-first: `@import "tailwindcss"` plus the `@theme` blocks in `src/app/globals.css`. The palette sits in a plain `@theme` because nothing overrides it at runtime. **If a token ever needs a media-query override, move it to a raw custom property on `:root` that `@theme inline` merely references** — `@theme inline` inlines a literal value into the utility it generates, so overriding that token later changes a variable nothing reads and the override silently does nothing. This bit both the old light/dark palette and the old display size.
- **`lg` is redefined to 981px** (`--breakpoint-lg`), because the design collapses to one column at 980px. `sm` (640px) is the mobile cut-off. Nothing uses `md` or `xl`.
- **Animation class names must not collide with Tailwind utilities.** `.grow`, for instance, is also `flex-grow: 1`; the keyframe hooks in `globals.css` are named `bar-grow`, `flow-dot`, `caret-blink`, and `type-line` for that reason.
- **Fonts** are Geist (`font-sans`) and Geist Mono (`font-mono`, with the slashed zero switched on through `--font-mono--font-feature-settings`), via `next/font/google` in the root layout and mapped through `@theme inline`.
- **The favicon is `src/app/icon.png`**, via the Next.js file convention — there is no `public/favicon.ico`. The share card is generated the same way, by `src/app/opengraph-image.tsx` with `next/og` — there is no `og.png`. `next/og` rasterises with satori, which needs *static* font files, so it reads Geist Regular, Geist SemiBold, and Geist Mono Regular from `assets/fonts/` with `node:fs`; the variable fonts `next/font/google` loads for the page cannot be reused there.
- **Dark only.** There is one palette, `color-scheme: dark` on `html`, no light theme, no `prefers-color-scheme` rule, and no `dark:` utilities.

## Conventions

- Import from `src/` via the `@/*` alias (`@/components/...`), configured in `tsconfig.json`. Content JSON sits outside `src/` and is imported relatively from `src/lib/content.ts`.
- Component files are kebab-case and export a named component: `section-head.tsx` exports `SectionHead`. Related components share a folder (`panels/`).
- TypeScript is `strict`; the ESLint config is `next/core-web-vitals` + `next/typescript`.
- `AGENTS.md` is regenerated by `next dev`. If it shows up dirty in `git status`, commit it with the work rather than reverting it.

## Code style

- Architecture-driven: decide structure first, then write. Prefer small,
  single-purpose modules over large files.
- Minimal comments. Code should read without them; comment only non-obvious
  decisions.
- No defensive programming. No speculative null checks, try/catch, or
  fallbacks for cases that can't occur.
- No emojis anywhere — code, UI copy, commit messages, docs.
- READMEs and docs stay concise. No marketing tone, no filler sections.

## Content

All copy, project data, and links live in `content/*.json` — `profile.json`, `nav.json`, `terminal.json`, `experience.json`, `projects.json`, `articles.json`, `certificates.json`, `sections.json`, `stack.json` — loaded through typed helpers in `src/lib/content.ts`. Components never hardcode copy. Section headings, leads, and the shell command shown beside each (`path`) or its one action (`action`) live in `sections.json`, keyed by section id and read by `SectionHead`. Short button labels ("View resume", "Email me") are the exception and sit in the components.

That extends to styling hooks: `profile.emphasis` names the substring of `headline` the hero sets in amber, so the emphasis follows the copy instead of being markup in a component.

Derived, not duplicated:
- The terminal's typing delays are computed from the order of its lines, and the `+N changes` count in Experience from the number of changes.
- `projects.json` panels are a discriminated union on `kind` (`cache`, `week`, `queue`); `components/panels/` has one component per kind. Panels drawn from made-up numbers carry a `tag` ("illustrative data") and must keep it.

## Images

`public/images/profile_picture.png` is the untouched original headshot. The hero shows it directly as a 112px rounded square through `next/image`, and `src/app/icon.png` (circular favicon) is derived from it. Regenerate from it rather than editing it.

`public/images/portrait-cutout.png` (the old background-removed hero portrait) and the scans under `public/certificates/` are no longer referenced by the page, but are still served at their URLs.

Everything under `public/` is served verbatim at its own URL, so a file there is public the moment it is committed, whether or not anything links to it. Check what a scan or document carries before adding it — the certificate scans were confirmed with Sailab as already public.

`sharp` is available as a Next.js dependency. From a script in the repo root:

```js
import { createRequire } from "node:module";
const sharp = createRequire(import.meta.url)("sharp");
```

A bare `import sharp` fails: the package is CommonJS, and Node resolves bare specifiers from the importing file's own directory, so a script written outside the repo cannot find it.

Replacing an image in place does not invalidate the Next.js image optimizer cache, which is keyed on the request URL — the old rendition keeps being served in dev. After overwriting a file under `public/`, `rm -rf .next/cache/images` and restart, or the page will show the previous version.

## Checking the UI

- **Narrow widths.** Resizing a real browser window will not go below roughly 1000px. Load the page in same-origin iframes at the target widths, or use Playwright's viewport resize.
- **Scrolling for screenshots.** `html` has `scroll-behavior: smooth`, so a scripted `scrollTo` animates and a screenshot taken right after catches the sticky header mid-move. Set `document.documentElement.style.scrollBehavior = "auto"` first.
- **The design side by side.** Serve `assets/design/` (`python3 -m http.server`) and open `Main.dc.html`; it does not load over `file://`.

## Deployment

Vercel handles deploys: push to `main` is production, PRs get previews.
GitHub Actions runs CI only (lint, typecheck, build) — never deploys.

In `.github/workflows/ci.yml`, `next build` must run **before** `npx tsc --noEmit`: `LayoutProps` and `PageProps` are generated into the gitignored `.next/types`, so a standalone typecheck on a clean checkout cannot resolve them.
